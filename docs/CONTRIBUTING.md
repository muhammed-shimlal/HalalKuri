# Contributing Guide

Welcome to the **Halal Kuri Management System** project.

This document defines the contribution standards, development workflow, coding conventions, documentation requirements, and quality expectations for anyone working on this project, including AI coding agents.

---

# Project Philosophy

This project is built around the following principles:

* Clean Architecture
* Readable Code
* Maintainability
* Security
* Performance
* Accessibility
* Scalability
* Consistency
* Simplicity
* Professional Quality

Every contribution should improve the project while preserving these principles.

---

# Documentation First Policy

Before writing or modifying any code:

1. Read the relevant documentation in the `/docs` directory.
2. Understand the existing architecture.
3. Follow the documented requirements.
4. Update the documentation if your changes affect behavior or implementation.

The documentation is considered part of the project's source code.

---

# Documentation Rules

All contributors and coding agents must follow these rules:

* Never delete any `.md` file.
* Never rename documentation files unless explicitly instructed.
* Never replace documentation with autogenerated content.
* Do not remove existing information unless it is obsolete and approved.
* Add new information while preserving existing content.
* Keep documentation synchronized with the implementation.

---

# Development Workflow

Follow this sequence when implementing features:

1. Review the relevant documentation.
2. Create or update the implementation plan.
3. Build the feature.
4. Test the feature.
5. Update documentation if necessary.
6. Verify that the project builds successfully.
7. Commit changes with a descriptive commit message.

---

# Branching Strategy

Recommended branch names:

```text id="e3r7gw"
main

develop

feature/<feature-name>

fix/<bug-name>

docs/<document-name>

refactor/<module-name>

hotfix/<issue-name>
```

Examples:

```text id="p4mhcm"
feature/member-dashboard

feature/announcement-system

fix/login-validation

docs/api

refactor/auth-module
```

---

# Commit Message Convention

Use clear and consistent commit messages.

Format:

```text id="mk6sd2"
type: short description
```

Examples:

```text id="vszboh"
feat: add contribution tracking

feat: create admin dashboard

fix: resolve login issue

docs: update deployment guide

style: improve homepage layout

refactor: simplify authentication module

perf: optimize report loading

security: hash passwords using bcrypt
```

---

# Code Standards

All code should:

* Be modular.
* Be reusable.
* Follow TypeScript best practices.
* Use meaningful names.
* Avoid duplication.
* Handle errors gracefully.
* Be easy to read.
* Follow consistent formatting.
* Include comments only where they add value.

---

# React Guidelines

Use:

* Functional Components
* Hooks
* TypeScript
* Component composition
* Reusable UI components
* Lazy loading where appropriate

Avoid:

* Large monolithic components
* Inline styles
* Deep prop drilling
* Duplicate logic

---

# Styling Guidelines

Use:

* Tailwind CSS
* shadcn/ui components
* Consistent spacing
* Responsive layouts
* Mobile-first design
* Accessible color contrast

Do not:

* Mix multiple styling systems unnecessarily.
* Use hard-coded colors when theme variables are available.
* Break the established design language.

---

# Performance Guidelines

Prioritize:

* Fast page loads
* Code splitting
* Lazy loading
* Optimized images
* Efficient rendering
* Small bundle sizes

Avoid unnecessary re-renders and unused dependencies.

---

# Security Guidelines

Always:

* Hash passwords.
* Validate user input.
* Protect restricted routes.
* Use environment variables for secrets.
* Follow the principle of least privilege.

Never:

* Commit API keys.
* Store passwords in plain text.
* Expose sensitive information in logs or API responses.

---

# Testing Checklist

Before submitting changes:

* Project builds successfully.
* No TypeScript errors.
* No linting errors.
* Responsive layout verified.
* Authentication verified.
* Navigation verified.
* Forms validated.
* Documentation updated if required.

---

# Pull Request Checklist

Before creating a pull request:

* Relevant documentation reviewed.
* Code follows project standards.
* No unnecessary files included.
* Build passes successfully.
* Changelog updated (if applicable).
* Documentation updated (if applicable).
* Commit messages are meaningful.

---

# Coding Agent Responsibilities

Any AI coding agent working on this project must:

* Read documentation before making changes.
* Follow the documented architecture.
* Preserve existing functionality unless instructed otherwise.
* Never delete or overwrite project documentation.
* Keep changes focused and modular.
* Avoid introducing breaking changes without approval.
* Keep code and documentation synchronized.

---

# Project Structure

Maintain a clean and organized directory structure.

Recommended layout:

```text id="zxmbm9"
src/
  components/
  pages/
  layouts/
  hooks/
  services/
  lib/
  utils/
  types/
  assets/

docs/

public/
```

New files should be placed in the appropriate directory and named consistently.

---

# Documentation Maintenance

Whenever a feature is:

* Added
* Modified
* Removed
* Refactored

Review the related documentation and update it if necessary.

Documentation should always reflect the current implementation.

---

# Final Rule

This project values long-term maintainability over short-term convenience.

Every contribution should leave the codebase, documentation, and developer experience better than before.

If a proposed change conflicts with the documented architecture or standards, the documentation should be consulted first, and any deviations must be explicitly approved before implementation.
